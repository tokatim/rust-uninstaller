# Разработка

## Рабочие договорённости

Документация и обсуждения ведутся на русском, идентификаторы в коде и коммиты — на
английском. Пользовательские строки хранятся в ресурсах локализации. Первая версия
интерфейса должна поддерживать русский и английский языки.

Каждая задача описывает: проблему, ожидаемое поведение, идентификаторы требований,
границы изменения и способ проверки. Удобный шаблон:

```text
Задача:
Требования: INV-01, INV-02
До / после:
Что входит:
Критерии приёмки:
Проверки:
```

Функциональная спецификация определяет поведение; roadmap определяет очередь работ.
Функция не считается реализованной из-за того, что она появилась в документации.

## Среда разработки

Начальная платформа — Windows 11 x64. На этапе M0 понадобятся Rust stable с MSVC
toolchain, C++ Build Tools и Windows SDK, Node.js LTS, npm и WebView2 Runtime.
Конкретные совместимые версии выбираются и фиксируются при создании приложения.
Установка инструментов на машину выполняется по отдельному указанию владельца.

На M0 добавить `rust-toolchain.toml`, `Cargo.lock`, `package-lock.json`, поле
`engines` и воспроизводимые команды в README. Для интерфейса использовать npm,
пока отдельный ADR не обоснует смену менеджера пакетов. Не смешивать lock-файлы
разных JS-менеджеров. Команды ниже — требования к будущему M0, сейчас они не работают:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
npm ci
npm run typecheck
npm run lint
npm test -- --run
npm run build
```

Точная рабочая директория каждой команды будет указана после создания workspace.
На M0 эти проверки должны стать настоящими командами CI; нельзя добавлять пустые
скрипты, которые всегда возвращают успех. Системные VM-проверки выполняются отдельно.

## Структура и код

- Системные правила и состояние операций принадлежат Rust. Бизнес-логику не дублировать в UI.
- Разделять обнаружение, нормализацию, планирование и исполнение. Получение списка
  программ не запускает команды удаления.
- Windows API прятать за узкими адаптерами. Сохранять код ошибки Windows и контекст операции.
- Ошибки типизированы; UI получает стабильный код и безопасное пояснение, а не сырой stack trace.
- Для путей и строк Windows сохранять корректное Unicode-представление; не требовать UTF-8 от ОС.
- Не строить команды конкатенацией пользовательского ввода. Сохранять семантику
  Windows command line при разборе зарегистрированных команд; использовать отдельные адаптеры.
- Блокирующие обходы диска и API не выполнять в UI-потоке. Операции сканирования
  поддерживают отмену и ограниченный параллелизм.
- Внешние данные считать недоверенными: реестр, package manifests, списки импорта,
  значки, строки версий и ответы дочерних процессов.
- `unsafe` допускается только там, где нужен для FFI; каждый блок объясняет lifetime,
  валидность указателей, владение handles и требования потоков.
- Новая зависимость требует причины, проверки лицензии, поддержки и размера поставки.
  Для заимствованного кода записывать источник, commit и уведомления.
- Секреты, сертификаты подписи и приватные данные никогда не хранить в репозитории.
- Исходники BCU доступны как pinned submodule `third_party/bcu`. Использовать существующие
  алгоритмы и правила по [плану переноса](docs/upstream-reuse.md), сохраняя происхождение.
  Apache-2.0 основного BCU не распространяется автоматически на сторонние компоненты.
  Подробности — [уведомления](THIRD_PARTY_NOTICES.md).

## Git

Основная ветка — `main`. На этапе документации небольшие завершённые изменения можно
коммитить прямо в неё. Для разработки функции использовать `feat/<short-name>`,
для исправления — `fix/<short-name>`, для документации — `docs/<short-name>`.
Создание дополнительных worktree не требуется без необходимости.

Перед изменениями: `git status --short` и просмотр относящегося к задаче diff.
Перед коммитом: проверки, `git diff --check`, явный `git add <files>`,
`git diff --cached --stat`, просмотр `git diff --cached`.
После коммита: `git status --short` и `git log -1 --oneline`.

Формат сообщений — Conventional Commits:

```text
docs: define project scope and development rules
feat(inventory): enumerate installed applications
fix(uninstall): handle reboot-required MSI exit code
test(cleanup): reject shared directories
chore: configure Windows build checks
```

Один коммит — одно логическое законченное изменение вместе с его проверками и
документацией. Не коммитить каждый промежуточный шаг. Не включать чужие правки.
Незавершённую работу сохранять в отдельной ветке с явным описанием состояния.

Автор настраивается локально через `git config --local`; глобальные настройки не
менять. Для публичных коммитов этого проекта используется имя Timoha и GitHub
`noreply`-адрес аккаунта tokatim; защиту личного email на GitHub не отключать.
Владелец 25 ноября 2026 года разрешил агенту самостоятельно делать коммиты,
обычный push, создавать публичный репозиторий, tags и релизы. Для этих действий после
проверок повторное подтверждение не требуется. Использовать CLI/API, без управления
компьютером. Секреты авторизации не печатать и не включать в remote URL.

После подключения remote использовать короткие ветки и PR. Агент может самостоятельно
объединять проверенный PR в рамках задачи; статусы CI должны быть успешны. До появления
CI выполнять доступные локальные проверки и явно фиксировать это ограничение.
Защиту основной ветки и обязательные проверки настроить при готовности настоящего CI.
Ошибочный опубликованный коммит исправлять новым коммитом или revert; историю без
указания не переписывать. Force push, удаление репозитория и вмешательство в чужие
репозитории не входят в обычное обслуживание.

Порядок и критерии самостоятельных выпусков — [releasing.md](docs/releasing.md).
Отсутствующий доступ к GitHub фиксируется как блокировка публикации, а не как
необходимость снова спрашивать разрешение пользователя на уже разрешённый push.

## Definition of Done

- Выполнены критерии затронутых требований текущего этапа.
- Обработаны ошибки и состояния отмены, ожидания прав и перезагрузки, если применимы.
- Пройдены релевантные проверки; пропущенные проверки и причины явно перечислены.
- Для системных изменений есть сценарий VM и свидетельство его выполнения.
- Нет случайных пользовательских данных, секретов и посторонних файлов в diff.
- Обновлены документация и CHANGELOG.md при изменении поведения.
- Создан локальный коммит; в отчёте есть его хеш и оставшиеся ограничения.

Для изменения только документации достаточно проверки внутренних ссылок,
согласованности требований и diff; запуск будущей сборки и фиктивные тесты не нужны.

Текущая проверка документов уже доступна и запускается из корня:

```text
python scripts/check_docs.py
git diff --check
```

Она проверяет локальные ссылки, блоки кода, уникальность и использование requirement IDs.
Она не является сборкой приложения или полным лицензионным аудитом upstream.
