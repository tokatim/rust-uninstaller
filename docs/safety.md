# Безопасность операций

Этот документ задаёт требования к продукту и разработке. Приложение ещё не
реализовано; перечисленное не является заявлением о существующей защите.

## Модель угроз

Недоверенные данные могут попасть из реестра, файловой системы, manifests,
импортированных списков и WebView. Возможные последствия — запуск подставленного
executable с повышенными правами, удаление общей папки, подмена IPC-запроса,
утечка списка программ или потеря данных при ошибочной очистке.

Основные активы: документы пользователя, состояние Windows, установленные программы,
учётные данные, административный токен и резервные копии. Сторонний деинсталлятор
сам может менять систему: приложение не гарантирует его добросовестность.

## Права и запуск

1. Основное приложение работает с обычными правами. Не требовать admin для сканирования.
2. UI не получает generic shell/file-write полномочий. Разрешения Tauri минимальны;
   CSP ограничена локальными ресурсами, загрузка remote content в privileged UI запрещена.
3. Исполнитель поддерживает определённые операции и adapters, валидирует executable,
   target identity, scope и режим по актуальному источнику.
4. Зарегистрированная команда не считается доверенной только потому, что она в реестре.
   Подозрительный путь, сетевой executable, неоднозначный shell/script или небезопасная
   запись требуют отказа/отдельного адаптера, а не автоматического повышения прав.
5. В первой версии блокировать запуск elevated executable из путей, контролируемых
   непривилегированным пользователем, пока отдельная модель проверки не принята ADR.
   Ограничение явно объяснять; не переносить такие файлы в доверенную папку незаметно.
6. Команда подтверждается в плане и проверяется непосредственно перед исполнением;
   validate-then-use race учитывается через безопасную работу с identity/handles,
   доступные гарантии API и отказ при недоказуемой безопасности.
7. Повышение прав не должно менять SID, к которому относится HKCU/per-user операция.
8. Не завершать глобальные msiexec, системные службы и процессы по одному имени.
9. Поддерживаемые параметры запрещают автоматический reboot; фактический reboot,
   инициированный сторонним кодом, регистрируется без ложных гарантий его предотвращения.

## Планирование и IPC

- Запрос конкретного пользователя привязан к конкретному плану, session и scope.
- Helper повторно проверяет цели и команды. Digest/nonce не заменяют caller authentication.
- ACL named pipe, локальность подключения, identity процессов, version negotiation,
  replay, message size и timeouts тестируются как отдельные security-сценарии.
- Если backend/helper потерял связь, UI не выдаёт неопределённый результат за успех
  и не запускает повторную операцию автоматически.
- При сбое хранения журнала новые разрушительные действия блокируются до устранения ошибки.

## Файловая система и реестр

- Сравнение путей учитывает компоненты, нормализацию Windows и реальную идентичность
  объекта. Строкового `StartsWith` недостаточно для проверки принадлежности каталогу.
- Reparse points, junctions, symlinks, UNC, device paths, hard links, ADS, case и
  alternate path forms учитываются явно; неподдерживаемые случаи не удаляются.
- Повторная проверка перед очисткой не должна превращаться в race между проверкой и действием.
- Корни дисков, Windows, пользовательских профилей, Program Files, AppData, ProgramData
  и другие общие каталоги не являются удаляемыми «остатками» целиком.
- Для known folders используется API; пути не строятся из предполагаемого имени пользователя.
- Общие runtimes, redistributables, shared package data и каталог издателя не очищаются
  только по совпадению названия. Наличие нескольких потребителей блокирует автоматический выбор.
- Реестр адресуется с явными hive/SID/view. Скан ограничен разрешёнными ветками;
  отсутствующая запись и отказ доступа — разные результаты.
- Команды «исправить запись» и «удалить программу» имеют разные результаты и тексты.

## Остатки и backup

Перед удалением объекта обязательны evidence, проверка защиты/общего использования,
актуальная identity и подтверждённый план. Пользовательские данные сохраняются
по умолчанию; массовый выбор не обходит это правило.

Для поддерживаемых объектов сначала создаётся проверяемая резервная копия/карантин
и manifest. Ошибка, нехватка места или неподдерживаемая семантика блокируют удаление
этого объекта по умолчанию. Резервирование сохраняет типы реестра, scope и
оговорённые метаданные файлов. Нельзя обещать полное восстановление ACL/streams
и специфических атрибутов без их реализации и теста.

Восстановление выполняется с нужными правами и проверкой destination; новый файл
или ключ не перезаписывается молча. Backup защищён ACL; срок хранения и удаление
карантина доступны явно. Точка восстановления Windows — дополнительная возможность,
а не обязательная доступная защита и не гарантия отката.

Ни backup остатков, ни Windows restore point не означают возможность транзакционно
отменить все действия чужого деинсталлятора. Кнопка «Отменить» не должна обещать это.

## Приватность и поставка

- Инвентаризация, заметки и история остаются локальными. Телеметрия не включена.
- В Git и CI не попадают реальные списки пользователя, SID, личные пути, secrets и backups.
- Диагностический экспорт показывает состав и редактирует личные поля; ошибки
  редактирования проверяются фикстурами. Передача по сети отсутствует по умолчанию.
- Зависимости и артефакты выпуска проверяются; keys подписи хранятся вне Git.
- Windows Authenticode и криптографическая подпись Tauri updater решают разные задачи;
  наличие одной не считается реализацией другой.
- Опасные изменения проверяются на VM со снимком. На рабочей машине допускаются
  read-only проверки и операции над явно созданными временными тестовыми данными.

## Release blockers

Подмена executable или IPC, удаление защищённого/общего объекта, потеря данных без
подтверждения, небезопасное восстановление и утечка private inventory блокируют
выпуск до исправления. После исправления нужен регрессионный тест на исходный сценарий.
