# GitHub и самостоятельные релизы

Владелец 25 ноября 2026 года делегировал агенту коммиты, обычные push, создание
публичного репозитория, ветки, PR, tags и публикацию релизов. Повторное разрешение
на каждый такой шаг не требуется. Использовать команды и GitHub API, без управления
компьютером. Платные действия, создание новых credentials, destructive операции
и смена лицензии не следуют автоматически из этого разрешения.

## Репозиторий

Целевой remote — публичный `tokatim/rust-uninstaller`; настройка и доступ проверяются
командами. Основная ветка — `main`. `origin` указывает только на собственный проект,
BCU закреплён отдельным submodule. Нельзя push в официальный репозиторий BCU.

Изменения собираются в логические коммиты, проверяются, затем отправляются обычным
push. Для функциональных изменений — короткая ветка и PR. Агент может самостоятельно
объединить PR при выполнении критериев; если CI существует, он должен завершиться успешно.
Если CI пока отсутствует, это явно указывается вместе с доступными локальными проверками.

Перед push проверить remote, staged/committed diff, отсутствие личных данных и
непреднамеренных артефактов. Токены не выводить, не записывать в Git и remote URL.
Реальные inventories, журналы и backup пользователя не публиковать.
Если GitHub отклонил ещё не опубликованные коммиты из-за приватного email,
исправить их на `noreply` с сохранением содержимого, затем повторить обычный push.
Настройки приватности аккаунта для этого не отключать; опубликованную историю не менять.

## Версии и момент выпуска

- Documentation-only изменения коммитятся и отправляются без создания версии приложения.
- Первый работающий прототип может получить `v0.1.0-alpha.1` после сборки и smoke-теста.
- Prerelease помечается `alpha`/`beta`/`rc` и GitHub prerelease; ограничения описываются явно.
- До 1.0 новые возможности — minor (`0.x.0`), исправления совместимого поведения — patch.
- `v1.0.0` возможна после выполнения критериев M6 или явного пересмотра scope владельцем.
- После 1.0 major — несовместимое изменение публичных CLI/форматов; minor — совместимые
  возможности; patch — исправления. Миграции данных проверяются независимо от номера.
- Каждый tag указывает на проверенный commit; уже опубликованный tag не передвигается.

Отсутствие приложения сейчас означает отсутствие оснований для app release.
Публичные исходники и документация могут быть опубликованы раньше бинарников.

## Обязательная последовательность выпуска

1. Проверить требования версии, текущую ветку/commit и чистое рабочее дерево.
2. Выполнить реальные build/static/unit/integration проверки и нужные VM-сценарии
   по testing.md. Отсутствующие команды не считать успешными.
3. Проверить compatibility, данные/backup, security blockers, зависимости и лицензии.
4. Обновить CHANGELOG, версию и ограничения; сохранить отчёт проверки.
5. Сформировать Windows-артефакты и проверить запуск в чистой VM. Нельзя выдавать
   сборку upstream BCU за Rust Uninstaller.
6. Добавить исходники или точные инструкции воспроизведения, LICENSE/NOTICE/third-party
   licenses и контрольные суммы. Если архив включает upstream, включить применимые
   лицензии всех вложенных компонентов. Обычный GitHub source archive не содержит submodule.
7. Для тестового prerelease допустим неподписанный бинарник с явной пометкой;
   обход предупреждений Windows пользователю не навязывается. Stable 1.0 требует
   выполнения DIST-03 либо явного пересмотра требования до выпуска.
8. Проверить отдельную подпись updater, если обновления включены; наличие Authenticode
   не заменяет проверку updater payload.
9. Создать draft release, проверить notes и assets, затем самостоятельно опубликовать
   как prerelease/stable согласно фактической готовности. Повторное согласование не нужно.
10. После публикации проверить tag/commit, доступность assets, SHA-256, release flags
    и отправить пользователю ссылку и ограничения.

Релиз не должен создавать сторонние расходы или требовать покупки сертификата
без отдельного указания владельца. Публикация блокируется при отсутствующем доступе,
проваленной проверке или security blocker; причина сообщается без ложного успеха.

## При обнаружении ошибки

Обычное исправление — новый patch/prerelease. Не заменять бинарник с тем же номером
незаметно и не переписывать опубликованную историю. При опасном дефекте предупредить
в release notes и остановить автоматические обновления через предусмотренный
механизм, затем выпустить проверенное исправление. Удаление релиза/репозитория,
force push и новая выдача прав требуют отдельного решения.
