# Правила работы агентов

Эти правила действуют во всём репозитории. Язык общения и документации — русский;
имена сущностей в коде и сообщения коммитов — английский. Прочитай README.md,
CONTRIBUTING.md и документы, относящиеся к задаче, перед изменениями.

## Область работы

- Выполняй текущую задачу до проверенного результата. Не добавляй несвязанные функции.
- Не выдавай описание, макет, заглушку или результат на фикстурах за готовую системную функцию.
- Сохраняй чужие незакоммиченные изменения. Проверяй `git status` перед редактированием и коммитом.
- Не запускай подагентов без явной просьбы пользователя.
- Повседневные обратимые изменения внутри задачи делай самостоятельно.
- Новый облачный сервис, платная зависимость, публикация, remote, push, релиз,
  смена лицензии и установка системных инструментов требуют отдельного указания владельца.

## Безопасность системного приложения

- Не запускай удаление, очистку, изменение автозапуска/служб, завершение посторонних
  процессов и экспериментальные системные операции на рабочей машине для проверки кода.
  Используй фикстуры, временные тестовые данные или специально подготовленную VM.
- Сканирование только читает данные. Повышение прав применяется к конкретной операции.
- UI передаёт идентификаторы и настройки; Rust проверяет команды, пути и полномочия.
- Никогда не добавляй универсальный вызов shell/PowerShell от имени администратора из UI.
- Не обещай универсальный тихий режим, полную очистку, точный освобождаемый объём
  или полный откат стороннего удаления.
- Изменения privileged helper, запуска команд, IPC, обработки путей и правил очистки
  сопровождай проверкой негативных сценариев по docs/testing.md.

## Код и проверка

- У системной логики единый источник истины в Rust; React отображает состояния.
- Unsafe изолируй на границе Windows API и объясняй инварианты в `SAFETY`-комментарии.
- Не используй `unwrap`/`expect` для внешних данных и восстанавливаемых ошибок.
- Зависимости добавляй по конкретной необходимости; фиксируй версии через lock-файлы.
- Не пиши формальные тесты на тривиальные косметические изменения. Системные правила,
  ошибки и границы доверия проверяй содержательными тестами.
- Выполни существующие релевантные проверки; отсутствующие команды не изображай выполненными.
- Не добавляй приватные инвентаризации, реальные логи пользователя, секреты и резервные копии в Git.

## Документация и коммиты

- При изменении поведения обновляй требования, этап и CHANGELOG.md в том же изменении.
- Новое архитектурное решение оформляй ADR. Непринятые решения помечай предложениями.
- Пользователь разрешил коммитить завершённые изменения: после проверки создавай
  логический локальный коммит без повторного запроса на каждый коммит.
- Добавляй файлы в индекс явным списком; перед коммитом проверяй staged diff.
- Не используй `git add .`, `git reset --hard`, `git clean -fd`, force push и переписывание
  опубликованной истории без прямого указания пользователя.
- Если коммит заблокирован средой, сохрани готовые файлы, объясни препятствие и не заявляй об успехе.
- В результате укажи изменение, выполненные проверки, ограничения и хеш созданного коммита.

Сейчас проект содержит только документацию. Команды сборки появятся на этапе M0;
до этого проверяются ссылки, согласованность требований, форматирование и Git diff.
